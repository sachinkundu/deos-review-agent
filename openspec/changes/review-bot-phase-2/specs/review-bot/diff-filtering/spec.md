## Purpose

Reduce low-signal input for correctness, API-reality, and tests review deterministically while preserving complete safety coverage and accurate GitHub line validation.

## ADDED Requirements

### Requirement: Classify lockfiles by exact basename
The system SHALL classify a changed path as a lockfile when its basename exactly and case-sensitively matches one of `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lock`, `bun.lockb`, `uv.lock`, `poetry.lock`, `Pipfile.lock`, `Cargo.lock`, `go.sum`, `Gemfile.lock`, `composer.lock`, `mix.lock`, or `flake.lock`.

#### Scenario: Listed lockfile is changed
- **WHEN** a changed path has one of the listed basenames
- **THEN** the path is classified as a lockfile

#### Scenario: Similar source filename is changed
- **WHEN** a changed path's basename does not exactly match a listed lockfile basename
- **THEN** the path is not classified as a lockfile by this rule

### Requirement: Classify vendored dependencies by path segment
The system SHALL normalize path separators to `/` and classify a changed path as vendored when any complete, case-sensitive path segment is `vendor`, `vendors`, `third_party`, `third-party`, `node_modules`, or `.terraform`.

#### Scenario: Vendored directory is changed
- **WHEN** a changed path contains one of the listed complete path segments
- **THEN** the path is classified as vendored

#### Scenario: Similar segment is changed
- **WHEN** a changed path contains text such as `vendor_api` but no complete listed segment
- **THEN** the path is not classified as vendored by this rule

### Requirement: Classify generated files by fixed path, filename, and marker rules
The system SHALL classify a changed path as generated when it has a complete, case-sensitive path segment `generated`, `__generated__`, `dist`, `build`, or `coverage`; when its basename matches the case-sensitive glob `*.generated.*`, `*.min.js`, `*.min.css`, `*.map`, `*_pb2.py`, or `*.pb.go`, where `*` matches zero or more basename characters; or when one of the first 20 non-blank lines of the right-side file contains `@generated` or contains both `generated` and `do not edit` using case-insensitive marker comparison.

#### Scenario: Generated path or filename is changed
- **WHEN** a changed path matches one of the fixed generated path segments or filename patterns
- **THEN** the path is classified as generated

#### Scenario: Generated marker is present
- **WHEN** one of the first 20 non-blank lines of the right-side file matches a fixed generated marker rule
- **THEN** the path is classified as generated

#### Scenario: Marker appears later in content
- **WHEN** a generated marker first appears after the first 20 non-blank lines of the right-side file and no path or filename rule matches
- **THEN** the path is not classified as generated by the marker rule

### Requirement: Apply fixed classification precedence
The system SHALL assign exactly one exclusion category to each filtered path using lockfile first, vendored second, and generated third when more than one rule matches.

#### Scenario: Path matches multiple categories
- **WHEN** a changed path matches more than one exclusion category
- **THEN** the system records the first matching category in lockfile, vendored, generated precedence order

### Requirement: Filter low-signal files before agent review
The system SHALL create an agent-review diff for the correctness, API-reality, and tests agents that excludes every path classified as a lockfile, vendored dependency, or generated file before those agents run.

#### Scenario: Lockfile changes are present
- **WHEN** the provider diff contains a file identified by the documented lockfile rules
- **THEN** that file's patch is absent from the agent-review diff

#### Scenario: Generated or vendored changes are present
- **WHEN** the provider diff contains a file identified by the fixed generated-file or vendored-path rules
- **THEN** that file's patch is absent from the agent-review diff

#### Scenario: Ordinary source changes are present
- **WHEN** a changed file matches none of the documented exclusion rules
- **THEN** its complete patch remains in the agent-review diff

#### Scenario: Identical input is filtered repeatedly
- **WHEN** the same provider diff and filter rules are processed more than once
- **THEN** the resulting agent-review diff and exclusion records are identical

### Requirement: Record every filtered file for auditability
The system SHALL retain a filter manifest with the review-run artifacts that records every excluded path, its assigned category, and the exact matched rule. Review agents SHALL NOT be required to read this manifest.

#### Scenario: Review input omits files
- **WHEN** one or more file patches are excluded from the agent-review diff
- **THEN** an operator can inspect the filter manifest to determine exactly which changed paths the correctness, API-reality, and tests agents did not review and why

#### Scenario: No files are filtered
- **WHEN** no changed file matches an exclusion rule
- **THEN** the retained filter manifest contains no exclusion records

### Requirement: Preserve the provider diff for safety, validation, and posting
The system SHALL retain the complete, unmodified provider-originated diff separately from the agent-review diff and SHALL use the complete diff for safety review, right-side line validation, and GitHub review posting.

#### Scenario: A file is filtered from agent input
- **WHEN** a changed file is excluded from the agent-review diff
- **THEN** its patch remains present in the complete provider diff supplied to the safety agent and used by downstream line validation

#### Scenario: Finding locations are validated
- **WHEN** the coordinator emits final findings
- **THEN** every location is validated against the complete provider diff rather than the filtered agent-review diff

### Requirement: Filtering does not select the agent roster
The system SHALL treat diff filtering only as input reduction and SHALL NOT use file exclusions, diff size, paths, or inferred pull-request risk to skip a Phase 2 review agent.

#### Scenario: Every changed file is filtered
- **WHEN** all changed file patches match exclusion rules
- **THEN** the correctness, API-reality, and tests agents run with the shared context and empty agent-review diff while the safety agent runs with the shared context and complete provider diff
